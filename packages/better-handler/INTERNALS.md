# Internals

Notes for whoever maintains this package. Nothing here is public surface; the README is the authority for what an app author may rely on.

## Nuxt 5 seams

Each mechanism Nuxt 5 replaces sits behind one function. Everything else in the package calls through it, so the Nuxt 5 adapter rewrites the function bodies and touches no caller.

| Seam                      | Function                             | File                          | Nuxt 4 today                                                                       | Nuxt 5                                 |
| ------------------------- | ------------------------------------ | ----------------------------- | ---------------------------------------------------------------------------------- | -------------------------------------- |
| Handler construction      | `makeEventHandler(run)`              | `src/runtime/shared/h3.ts`    | h3 v1 `defineEventHandler`                                                         | h3 v2 `defineHandler`                  |
| Error construction        | `httpError(input)`                   | `src/runtime/shared/h3.ts`    | h3 v1 `createError`; `message` set, `statusMessage` never                          | h3 v2 `HTTPError`; `data` stays nested |
| Nitro plugin registration | `addRuntimeServerPlugin(path)`       | `src/build/server-plugins.ts` | kit `addServerPlugin`                                                              | kit `addNitroPlugin` variants          |
| Route discovery           | `addRouteTypeTemplate(nuxt, render)` | `src/build/routes.ts`         | `nitro.scannedHandlers` and `nitro.options.handlers`, re-emitted on `types:extend` | Nuxt's `server:routes` hook            |
| Response typing           | `Wire`, `RouteKeyOf`, `RouteMethod`  | `src/runtime/types/engine.ts` | `nitropack/types` `Serialize`/`Simplify` and `MatchedRoutes`; h3's `RouterMethod`  | Nuxt's generated route engine          |

The route discovery seam is the only code that reads Nitro's handler list or hooks Nitro; the renderer it calls, `emitMap` in `src/build/emit-map.ts`, never sees Nitro. The response-typing seam is the only importer of `nitropack/types`, and the generated map names only `@dphonys/better-handler/types`, so the generated file survives the move to the generated engine unchanged. The package depends on no `nitropack` of its own: the import is type-only, and every Nuxt 4 app's generated tsconfig maps `nitropack/types` onto the app's own Nitro (Nuxt hoists it from 4.0.0), which is the one whose `InternalApi` the lookups must read; route discovery restates Nitro's `resolveNitroPath` with `pathe`. A `nitropack` dependency would also re-resolve the workspace lockfile into a second Nitro copy that breaks the old packages' typecheck. Slice 05 adds the fetch family's members to the response-typing seam (`FetchRequest`, `RouteMethodOf`, `ResponseOf`, `VanillaFetchOptions`, `FetchDefaults`, `RawFetchResponse`, `WireInput`) and the request-inputs slot to the map.

No runtime name in the h3 seam may be an h3 v2 export: Nuxt 5 auto-imports every lowercase one.

## Shared plumbing

- **The `devChecks` flag** (`src/runtime/server/dev-checks.ts`): starts as `import.meta.dev`, and the Nitro plugin `src/runtime/server/plugins/dev-checks.ts`, registered only when the app sets `devChecks: false`, turns it off.

## errors

- **Declaration-time checks** (`src/runtime/server/errors/declaration.ts`): `resolveErrors` runs each rule over every entry before the next rule starts: reserved tag, then a schema that is not a Standard Schema, then a status outside 400 to 599, then a key an entry does not take. `defineError` checks its one-key map the same way. Every refusal is a `declarationFault`, a plain `Error` with the `[better-handler]` prefix.
- **The Fail helper** (`src/runtime/server/errors/fail.ts`): returns an `Error` subclass with `_tag` and the fields as own enumerable properties, defined rather than assigned so a field named `message`, `name`, `stack` or `cause` is the field. Its tag lookup is prototype-less. A call the types would refuse is a `developerFault`, a plain `500` with no `data`.
- **The composing wrapper** (`src/runtime/server/define-better-event-handler.ts`): `defineBetterEventHandler` holds the errors half for now. At declaration it resolves the `errors` map and builds the Fail helper once; per request it hands the Handler a fresh `{ fail }` context and answers whatever the Handler throws through the boundary. The io half and the returned handler's brands extend this same function.
- **Recognition at the boundary** (`src/runtime/server/errors/boundary.ts`): a thrown value whose string `_tag` (read by property access, so a prototype's counts) is a declared key goes out through `httpError` with the declared status, the tag as `message` and `data` = `{ _tag, ...own enumerable fields }`. Function-valued fields are left out, as JSON would leave them out, which also keeps a `toJSON` field from replacing the whole of `data`. Everything else, an undeclared tag included, is rethrown as it was thrown.
- **The two errors development checks**, behind the `devChecks` flag and each a `developerFault`: the thrown-fields check validates the whole Tagged error, `_tag` included, against the entry's schema (an Effect error class's schema requires `_tag`; a strict schema that does not list `_tag` therefore refuses, and an Effect field named `message`, which Effect keeps non-enumerable, never goes out and is reported), awaiting an asynchronous one and discarding its output; the undeclared-tag check refuses a string `_tag` the route does not declare, naming it and the declared tags.
- **The fields guard** (`FieldsRule` in `src/runtime/types/errors/declaration.ts`): a schema output field holding a `bigint` or a `symbol`, at any depth, is refused at the key. Functions are not refused and `toJSON` is not reserved: an Effect error class's output type carries methods, `toJSON` among them, which live on the prototype and never go out, so refusing them would refuse every Effect error.
- **The server recognizer** (`src/runtime/server/errors/recognize-known-error.ts`): reads the error's own `data` through `taggedOf` (`src/runtime/shared/errors/tagged.ts`), one depth only, so a callee's Known error a caller let escape is not recognised.
- **The Known-errors slot** (`src/runtime/types/handler.ts`): `BetterEventHandler` carries the route's Known errors under a module-private `unique symbol` key, so a foreign handler cannot spoof it; `KnownErrorsOfHandler` reads it, answering `never` for `any`, for an unbranded handler and for an index signature. Each variant is `{ _tag }` beside the fields the boundary sends (`KnownErrorsOf` in `src/runtime/types/errors/tagged.ts`): a schema output's keys without `_tag` and without methods, and on a class instance - an `Error` carrying methods, as an Effect error class is - without `Error`'s own keys and the `~`-prefixed markers kept on its prototype. An untyped schema contributes its tag alone.
- **The generated `KnownApiErrors` map** (`src/build/emit-map.ts`, through the route discovery seam): one `declare module '@dphonys/better-handler/types'` block keying every route Nitro serves by route and lowercased method, each value `Wire<KnownErrorsOfHandler<typeof import('…').default>>`. It is not hoisted; the package's `exports` resolves the specifier from every generated tsconfig. `KnownErrorsOfRoute` looks a request path up through `RouteEntry` (`src/runtime/types/utils.ts`: the lowercased method, then `default` by key presence) and reads an `any` entry - a handler module the compiler cannot resolve, such as a module's `.mjs` route or Nuxt's renderer - as `never`, boxed in tuples because the compiler's error type survives every conditional type over it.
