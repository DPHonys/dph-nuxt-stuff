# Internals

Notes for whoever maintains this package. Nothing here is public surface; the README is the authority for what an app author may rely on.

## Nuxt 5 seams

Each mechanism Nuxt 5 replaces sits behind one function. Everything else in the package calls through it, so the Nuxt 5 adapter rewrites the function bodies and touches no caller.

| Seam                      | Function                                                                                                                                                                 | File                          | Nuxt 4 today                                                                                                                                                                                                             | Nuxt 5                                 |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------- |
| Handler construction      | `makeEventHandler(run)`                                                                                                                                                  | `src/runtime/shared/h3.ts`    | h3 v1 `defineEventHandler`                                                                                                                                                                                               | h3 v2 `defineHandler`                  |
| Error construction        | `httpError(input)`, `toNuxtError(cause)`, `isNormalisedError(value)`                                                                                                     | `src/runtime/shared/h3.ts`    | h3 v1 `createError` and `isError`; `message` set, `statusMessage` never                                                                                                                                                  | h3 v2 `HTTPError`; `data` stays nested |
| Nitro plugin registration | `addRuntimeServerPlugin(path)`                                                                                                                                           | `src/build/server-plugins.ts` | kit `addServerPlugin`                                                                                                                                                                                                    | kit `addNitroPlugin` variants          |
| Route discovery           | `addRouteTypeTemplate(nuxt, render)`                                                                                                                                     | `src/build/routes.ts`         | `nitro.scannedHandlers` and `nitro.options.handlers`, re-emitted on `types:extend`                                                                                                                                       | Nuxt's `server:routes` hook            |
| Response typing           | `FetchRequest`, `RouteMethod`, `RouteMethodOf`, `RouteKeyOf`, `ResponseOf`, `VanillaFetchOptions`, `FetchDefaults`, `RawFetchResponse`, `Wire`, `VanillaUseFetchOptions` | `src/runtime/types/engine.ts` | `nitropack/types` `NitroFetchRequest`, `AvailableRouterMethod`, `MatchedRoutes`, `TypedInternalResponse`, `NitroFetchOptions`, `$Fetch['create']`, `Serialize`/`Simplify`; h3's `RouterMethod`; Nuxt's `UseFetchOptions` | Nuxt's generated route engine          |

The route discovery seam is the only code that reads Nitro's handler list or hooks Nitro; the renderer it calls, `emitMap` in `src/build/emit-map.ts`, never sees Nitro, and renders both slots of the one generated map (`BETTER_HANDLER_MAP`) from the same route list. `VanillaUseFetchOptions` is Nuxt's own `useFetch` options at a string path and a lowercase method the path has: the one spelling both Nuxt 4.0's declaration (a `NitroFetchRequest` path, Nitro's methods for it) and 4.6's (any string, any method in either case, request keys by route engine) accept; the composables omit every key that differs by version or engine. The response-typing seam is the only importer of `nitropack/types`, and the generated map names only `@dphonys/better-handler/types`, so the generated file survives the move to the generated engine unchanged. The package depends on no `nitropack` of its own: the import is type-only, and every Nuxt 4 app's generated tsconfig maps `nitropack/types` onto the app's own Nitro (Nuxt hoists it from 4.0.0), which is the one whose `InternalApi` the lookups must read; route discovery restates Nitro's `resolveNitroPath` with `pathe`. A `nitropack` dependency would also re-resolve the workspace lockfile into a second Nitro copy that breaks the old packages' typecheck. The fetch family reads every route lookup, response and vanilla option through the seam (see the fetch family below). `RawFetchResponse<T>` is spelled `Response & { _data?: T }`, not indexed out of `ReturnType<$Fetch['raw']>`, which instantiates Nitro's generic `raw` at its constraints and makes a failing `.raw` call report TS2321. There is no `WireInput`: the request-inputs slot names no Nitro type at all (see io below).

The native slot (`NativeRequest`, `src/runtime/types/io/native.ts`) is written against h3 v1's `EventHandlerRequest`, which Nuxt 4.6's extractor reads; it is the one type the Nuxt 5 adapter restates for h3 v2's event, and the only one that knows what an h3 query can carry.

No runtime name in the h3 seam may be an h3 v2 export: Nuxt 5 auto-imports every lowercase one.

## Shared plumbing

- **The `devChecks` flag** (`src/runtime/server/dev-checks.ts`): starts as `import.meta.dev`, and the Nitro plugin `src/runtime/server/plugins/dev-checks.ts`, registered only when the app sets `devChecks: false`, turns it off.

## The fetch family

- **The global** (`src/runtime/shared/better-fetch.ts`): `createBetterFetch(base)` wraps a vanilla `$fetch` instance; every member (the call, `.raw`, `.native`, `.create`) forwards to its namesake, adding only the header below, and `.try` runs the call through `toTryResult`. `create(defaults)` threads the instance's headers the way ofetch's shallow defaults spread does, so a later `create` with `headers` replaces the earlier ones. `$betterFetch` is one object built over `lazyGlobalFetch`, which reads `globalThis.$fetch` when called, so the global exists before either side installs `$fetch`. Two plugins install it: `src/runtime/app/plugins/better-fetch.client.ts` in the browser, and the Nitro plugin `src/runtime/server/plugins/better-fetch.ts` on the server, whose `globalThis` server-side rendering shares.
- **The event-bound fetch** (`src/runtime/server/event-better-fetch.ts`): the same Nitro plugin registers `installEventBetterFetch` on the `request` hook, the earliest point `event.$fetch` exists. The instance is the call and `.try` only, as `event.$fetch` is a bare closure over h3's `fetchWithEvent` with nothing to back `.raw` or `.create`. It reads `event.$fetch` on every call, so it composes with a later replacement, and checks once: a missing `event.$fetch` on the first call is `EventFetchUnavailableError`, naming the version skew, thrown outside `.try`'s classification; after a verified call it is the `TypeError` the bare call would raise.
- **The `accept` header**: the global, the event-bound fetch and the fetch composables each add `accept: application/json` (`ACCEPT_JSON`, one constant in `src/runtime/shared/better-fetch.ts`) unless the caller, per call or per `create` instance, sent an `accept` of its own. Nitro answers an error as JSON outside `/api/**` only to a request asking for JSON, so without it a Known error from a `server/routes/` route arrives as an HTML page and is classified `request-failed`; `test/e2e/fetch-wire.ts` shows both answers. The global builds the merge through a `Headers` and hands one on, which ofetch merges correctly; the event-bound one and the composables flatten to a plain object, because `fetchWithEvent` merges by object spread and a `Headers` spreads to nothing. h3 never forwards the incoming request's own `accept`. No other header is sent.
- **The composables** (`src/runtime/app/composables/`): one `(name, lazy)` factory per kind, `betterFetchComposable` and `betterAsyncDataComposable`, each delegating to Nuxt's own `useFetch`/`useLazyFetch` or `useAsyncData`/`useLazyAsyncData` (never `lazy: true`, and never `createUseFetch`, which Nuxt 4.0 lacks) and naming the function it returns. `useRequestBetterFetch` hands back the rendered request's `event.$betterFetch` during server-side rendering and the global elsewhere. One table in `src/module.ts` drives both `addImports` and `optimization.keyedComposables` (`argumentLength: 3`, vanilla's own), so the compiler appends a key to a call as it does to vanilla's; a keyless `useBetterAsyncData` has no key without it. Nuxt 4.0's compiler keys a call only when the composable was auto-imported (or imported by the exact `source` registered); one imported by a relative path is read as a foreign function and left unkeyed, which is why `test/fixtures/fetch/app.vue` calls them through auto-imports, typed for the package's own typecheck by `auto-imports.d.ts` beside it. Both wrappers keep vanilla's variadic runtime signature: the fetch one merges only the `accept` header into the options, through a `computed` flattened to a plain object (h3's `fetchWithEvent` merges headers by spread, and vanilla deep-watches the option), reading refs at every level; the async-data one finds the handler by vanilla's own `_isAutoKeyNeeded` rule, so a ref or getter key is a key and an appended key stays last, and substitutes a handler that resolves a success to its `data` and throws a failure.
- **What a failure rethrows as** (`failureOrigin` in `src/runtime/shared/errors/try-result.ts`): a `.try` error is a plain variant, which Nuxt's `useAsyncData` would wrap with `createError` into a `500` holding no body. `classifyFailure` links every variant it hands out to the `NuxtError` it read the variant off (the Request-failed variant to its `cause`), and the async-data wrapper throws that error, which Nuxt's `createError` hands on untouched: the `error` ref keeps the response body, the Tagged error at `data.data` and the status. The link is a `WeakMap` on the realm's `globalThis` under `Symbol.for('@dphonys/better-handler/failure-origins')`, not module state and not a property of the variant: during server-side rendering the `.try` runs in Nitro's copy of the module (the global and `event.$betterFetch` are Nitro's) and the composable in the app bundle's, and Nuxt's payload serializer refuses an object with a symbol key. A variant the family did not classify, such as a copy, is thrown as the `NuxtError` Nuxt would have made of it. `test/e2e/fetch-wire.ts` fails on both servers with the link made module-local.
- **The composables' types** (`src/runtime/types/composables.ts`): `UseBetterFetchOptions` is `VanillaUseFetchOptions` without `method`, `body`, `query`, `headers` and `params`, with `method?: M` and the fetch family's sources re-added reactive (`ComputedOptions`, Nuxt's verbatim). Keeping Nuxt 4.6's `method` reports an excessive stack depth at the call site with the flag off (ticket 10). `UseBetterAsyncData` is written against what 4.0 and 4.6 both declare: the handler is vanilla's own, read off `Parameters<typeof useAsyncData>` (`AsyncDataHandler` is 4.6's alone, and so is the `{ signal }` it is handed), the options are `AsyncDataOptions`, and `KeysOf` is read off its `pick` option. The handler's result type is inferred unconstrained and checked inside the handler's own return type (`Result & TryResultCheck<Result>`), so a handler that forgot `.try` is refused at what it returns, naming `AsyncDataHandlerError`. Not a constraint: the constraint is the contextual type of the handler's return, from which a bare `$betterFetch` call infers its response type, which reports TS2321 while the route is still being inferred. Not a check intersected with the handler either: resolving it for the handler's parameters fixes the result type before a handler naming its parameters is read. The `error` ref is `KnownErrorOf` the handler's failures minus `RequestFailed`, as `KnownErrorFor` is the route's.
- **Request typing** (`src/runtime/types/fetch.ts`): variant C. Every member's call is `<T, R, const M extends MethodArg<R> = DefaultMethod<R>>(request: R, opts?: BetterRequestOptions<R, M>)`, `MethodArg` being Nitro's methods for the route in either case and `DefaultMethod` `get` when the route has one. `BetterRequestOptions` is vanilla's options without `method`, `body`, `query`, `headers` and `params`, with `method?: M` and the three sources re-added from `RequestInputOfRoute` (the lowercased method, then `default` by presence): a declared `body` or `query` is its schemas' input type, required iff `{}` is not assignable to it (so an input admitting `undefined` but not `{}` is required), and closed by TypeScript's excess-property check; declared `headers` are a record whose named keys are typed and whose other keys stay open strings, since a client sends more headers than a route validates; an undeclared source is vanilla's own. A route of this package (an entry, even `{}`) takes no `body` on `get` and `head`; a route the map does not type (`never`: unbranded, unresolvable, a `Request` object) keeps vanilla's options key for key, `body` on `get` included, minus `params`. The stack-depth rules sit beside the types: `M`'s default references only `R`, a method derived from the options lives in an alias default and never in a signature parameter's constraint, the route lookup runs once per map lookup, and no type parameter appears in its own constraint. `$betterFetch<T, R, M>` is not type-argument-compatible with `$fetch<T, R, O>`.
- **Responses and `.try`**: the response is `ResponseOf` (Nitro's `TypedInternalResponse`), so the declared output's output type as JSON carries it; `.try`'s error is `KnownErrorsOfRoute` for the call's route and method plus `RequestFailed`, exhaustive on `_tag`; a thrown error is `KnownErrorFor`.
- **Where the call-site types are proved**: `test/fixtures/native/checks/better-fetch.ts` and, for the composables, `checks/composables.ts`, compiled by `test/e2e/native-engine.test.ts` in the app's program on Nitro's route types and, on Nuxt 4.6 and later, on the generated route engine, refusing exactly its marked lines, the same in both. The fixture installs the built module, so every declaration of the package in its program is the shipped `.d.ts`: installed from `src`, the app's program holds the package's declarations in source form, through the plugin types Nuxt generates, and checking a call site first reports TS2321 on those declarations, an order no consumer meets.
- **The route ceiling**: on Nitro's `InternalApi` engine every call statement of the family, as of vanilla `$fetch` with the flag off, passes TypeScript's per-statement instantiation cap somewhere between 176 and 201 routes and reports TS2589 (ticket 10's measurement). Accepted; it lifts when the Nuxt 5 adapter moves the response-typing seam to the generated engine. There is no version-conditional typing before then.

## errors

- **Declaration-time checks** (`src/runtime/server/errors/declaration.ts`): `resolveErrors` runs each rule over every entry before the next rule starts: reserved tag, then a schema that is not a Standard Schema, then a status outside 400 to 599, then a key an entry does not take. `defineError` checks its one-key map the same way. Every refusal is a `declarationFault`, a plain `Error` with the `[better-handler]` prefix. The compile guard catches the same mistakes earlier where it can: a status written as a numeric literal outside 400 to 599 is refused at its `status` key (`StatusRule`), while a plain `number` is left to the throw.
- **The Fail helper** (`src/runtime/server/errors/fail.ts`): returns an `Error` subclass with `_tag` and the fields as own enumerable properties, defined rather than assigned so a field named `message`, `name`, `stack` or `cause` is the field. Its tag lookup is prototype-less. A call the types would refuse is a `developerFault`, a plain `500` with no `data`.
- **The composing wrapper** (`src/runtime/server/define-better-event-handler.ts`): `defineBetterEventHandler` holds the errors half and both sides of the io half. At declaration it first refuses, with a `declarationFault`, options that are not an object and an `errors` that is not a map - what an untyped caller can hand it that would otherwise end in a `TypeError` - then resolves the `errors` map, then plans the `input`, then resolves the `output` (see io below), and refuses a route that declares no source, no tag and no reply (`must declare input, errors, output, or any combination`; an empty map counts for nothing). It builds the Fail helper once, only when `errors` declares a tag, and settles the context's helpers once (`fail`, and `respond` for a status map). Per request it validates the input before the Handler is entered and outside the boundary, hands the Handler a fresh context (the validated sources plus the helpers), answers whatever the Handler throws through the boundary on a route that declares `errors` (a route without `errors` has no boundary, so its throws propagate untouched), and then, outside the boundary, sends the settled return through the output delivery, so a refusal of the response is never read as something the Handler threw. The returned Handler also fills h3's `H3Event<Request>` slot (see the native slot under io); the callback's own `event` stays h3's default.
- **One Known-error construction** (`src/runtime/server/errors/known-error.ts`): `createKnownError(status, tagged)` builds every Known error through `httpError`, the tag as `message` and the Tagged error as `data`. The boundary and the Built-in validation-failed variant both go through it, so `recognizeKnownError` and the client classifier read one shape.
- **Recognition at the boundary** (`src/runtime/server/errors/boundary.ts`): a thrown value whose string `_tag` (read by property access, so a prototype's counts) is a declared key goes out through `httpError` with the declared status, the tag as `message` and `data` = `{ _tag, ...own enumerable fields }`. Function-valued fields are left out, as JSON would leave them out, which also keeps a `toJSON` field from replacing the whole of `data`. Everything else, an undeclared tag included, is rethrown as it was thrown.
- **The two errors development checks**, behind the `devChecks` flag and each a `developerFault`: the thrown-fields check validates the whole Tagged error, `_tag` included, against the entry's schema (an Effect error class's schema requires `_tag`; a strict schema that does not list `_tag` therefore refuses, and an Effect field named `message`, which Effect keeps non-enumerable, never goes out and is reported), awaiting an asynchronous one and discarding its output, and turning a schema that throws or rejects into a fault naming the route and tag, with what it threw as the `cause`; the undeclared-tag check refuses a string `_tag` the route does not declare, naming it and the declared tags, and keeps the thrown value as the fault's `cause`, since a `_tag` is not only ours (Effect's own failures carry one) and its stack is what finds the bug. h3 never sends a `cause`, so it reaches the logs and an error hook, not the wire.
- **The fields guard** (`FieldsRule` in `src/runtime/types/errors/declaration.ts`): a schema output field holding a `bigint` or a `symbol`, at any depth, is refused at the key. Functions are not refused and `toJSON` is not reserved: an Effect error class's output type carries methods, `toJSON` among them, which live on the prototype and never go out, so refusing them would refuse every Effect error.
- **The server recognizer** (`src/runtime/server/errors/recognize-known-error.ts`): reads the error's own `data` through `taggedOf` (`src/runtime/shared/errors/tagged.ts`), one depth only, so a callee's Known error a caller let escape is not recognised.
- **The Known-errors slot** (`src/runtime/types/handler.ts`): `BetterEventHandler` carries the route's Known errors (`RouteKnownErrors`: the declared variants, plus `ValidationFailed` exactly when the route declares a source) under a module-private `unique symbol` key, so a foreign handler cannot spoof it; `KnownErrorsOfHandler` reads it, answering `never` for `any`, for an unbranded handler and for an index signature. Each variant is `{ _tag }` beside the fields the boundary sends (`KnownErrorsOf` in `src/runtime/types/errors/tagged.ts`): a schema output's keys without `_tag` and without methods, and on a class instance - an `Error` carrying methods, as an Effect error class is - without `Error`'s own keys and the `~`-prefixed markers kept on its prototype. An untyped schema contributes its tag alone.
- **The generated `KnownApiErrors` map** (`src/build/emit-map.ts`, through the route discovery seam): one `declare module '@dphonys/better-handler/types'` block keying every route Nitro serves by route and lowercased method, each value `Wire<KnownErrorsOfHandler<typeof import('…').default>>`. It is not hoisted; the package's `exports` resolves the specifier from every generated tsconfig. `KnownErrorsOfRoute` looks a request path up through `RouteEntry` (`src/runtime/types/utils.ts`: the lowercased method, then `default` by key presence) and reads an `any` entry - a handler module the compiler cannot resolve, such as a module's `.mjs` route or Nuxt's renderer - as `never`, boxed in tuples because the compiler's error type survives every conditional type over it.
- **The client classifier** (`classifyFailure` in `src/runtime/shared/errors/try-result.ts`): a failure whose fetched body carries a Tagged error at `data` (the error's `data.data`) is that Tagged error, handed back itself; anything else is the Request-failed variant, its `status` read off the thrown value before h3's normalisation (so `undefined` when no response arrived) and its `cause` from `toNuxtError`. An error h3 already normalised, such as a `useFetch` error ref, carries h3's default `500` for a request that got no response, so its status is read off its own `cause`, which h3 sets to what it normalised: ofetch's error when a response arrived, the network or abort error when none did. `toNuxtError` hands an error h3 already made back as it is and defines nothing on it, since it is the caller's object. `toTryResult` runs a call through it and rethrows nothing; slice 05's `.try` is built on it. `matchError` (`src/runtime/shared/errors/match-error.ts`) takes a `.try` error as it is and a fetched `NuxtError` through the same classifier, reads a ref once, looks arms up with `Object.hasOwn`, and calls the required fallback for a tag no arm names.

## io

- **The plan** (`src/runtime/server/io/plan.ts`): `sourcePlan(input)` runs at declaration and throws a `declarationFault` at the first rule broken: an `input` that is not a map, then a key that names no Validation source (checked over the author's keys before the walk, which visits only the four sources and would otherwise skip a misspelling silently), then a slot that is not a Standard Schema, a tuple element that is not one (named by index), or an empty tuple. A slot left `undefined` declares nothing. Each step keeps its schemas as a non-empty list and whether the author wrote a tuple, so a sentence names an element by index only for a tuple. The Standard Schema test is `isStandardSchema` from `src/runtime/shared/guards.ts`; no schema library is imported at runtime.
- **The walk** (`validatedContext`): sources in `VALIDATION_SOURCES` order (`src/runtime/shared/io/sources.ts`), `route -> query -> headers -> body`, whatever the declaration's key order; the first source with issues raises, so a later source, the body included, is never read. Within a source every element runs, in tuple order and one after another, so all its issues arrive together. A result is a success when `issues` is `undefined`, so a value-less success stays a success; an `issues: []` result is a `developerFault` naming the route, the source and the element, raised only after the siblings had their say. A lone element, bare or a tuple of one, passes its output through untouched; a tuple's outputs merge later-wins with `Object.defineProperty`, so a `__proto__` key stays an own key, and an output that is not a plain object (a null prototype passes, as h3's form body has one) is a `developerFault`. A `validate` that throws propagates as it was thrown.
- **The source readers** (`src/runtime/server/io/sources.ts`): with the h3 seam, the only file importing h3 runtime helpers (`getRouterParams` with `decode`, `getQuery`, `getRequestHeaders`, `readBody`). The body is read only on h3 v1's payload methods (`PATCH`, `POST`, `PUT`, `DELETE`); any other method validates `undefined`. The read is strict, as `readValidatedBody`'s is, and an h3 4xx from it (judged by status through `isNormalisedError`) becomes one body issue, `Request body could not be parsed`, the package's own message; a 5xx or a non-HTTP throw propagates. h3 memoises the parse, so a middleware's earlier non-strict read wins and the schema rejects the raw string instead.
- **Projection** (`src/runtime/server/io/issues.ts`): an issue is rebuilt as `{ source, message, path }`, nothing copied by filtering. A path segment is a key or an object carrying one, read with plain guards: a `null` segment stringifies, a null-prototype carrier is read like any other, a key that is a string or a number stays as it is, a symbol stringifies, and an object key is described rather than stringified, since `String()` throws on a null-prototype object.
- **The Built-in validation-failed variant** (`src/runtime/server/io/validation-failed.ts`): `raiseValidationFailed`, the `OnInvalid` door the wrapper hands the walk, throws `createKnownError(400, { _tag: 'validation-failed', issues })`. No second marker, no second recognizer; `validation-failed` stays a reserved tag in `resolveErrors` and the compile guard, and `fail` cannot name it because no route can declare it.
- **The input types** (`src/runtime/types/io/`): `InputOf`, `MergedInput` (a tuple's inputs intersected), `SourceInput` and `RequestInput` are the client side, `OutputOf`, `MergedOutput` (outputs merged element by element, so a union output stays a union), `SourceValue` and `ValidatedContext` the Handler's. A slot whose type admits `undefined` declares nothing (`DeclaredSource`), at the type level as at runtime. `InputGuard` refuses, at the offending key, a key beside a real source that names no source and a tuple whose outputs are not objects or share a named key; a misspelled key standing alone shares no key with `InputDeclaration`, so nothing is inferred for the guard and TypeScript's excess-property check refuses it instead. The options' declare-something guard is `HandlerDeclarationError` in `src/runtime/types/handler.ts`.
- **The Request-input slot** (`src/runtime/types/handler.ts`): `BetterEventHandler` carries `RequestInput<Input>` under a second module-private `unique symbol` key beside the Known-errors slot, read by `RequestInputOfHandler` with the same `any`/unbranded degradation; a branded route declaring no source carries `{}`.
- **The generated `KnownApiRequestInputs` map** (`REQUEST_INPUTS_SLOT` in `src/build/emit-map.ts`, rendered beside `KnownApiErrors` in the same file through the route discovery seam): each value is `RequestInputOfHandler<typeof import('…').default>`, unwrapped. No `Serialize`, as the schema input is what a client sends, and no nitropack `Simplify`, which turns `unknown` (a `z.coerce.*` input) into `{}` and so refuses a `null` the schema accepts. Several handlers on one route and method union. `RequestInputOfRoute` (`src/runtime/types/index.ts`) looks a request path up through the same `RouteEntry` and the same `any` guard as `KnownErrorsOfRoute`.
- **The native slot** (`NativeRequest` in `src/runtime/types/io/native.ts`): the `Request` of the `EventHandler<Request, Response>` that `defineBetterEventHandler` returns, so Nuxt 4.6's `RequestBodyOf`/`RequestQueryOf` type vanilla `$fetch` and `useFetch` on the route when an app turns `experimental.routeTypedFetch` on; the module never reads or sets the flag. It holds `body` and `query` only, each key present only when declared, as schema input types. Nuxt infers the slot through `H3Event<infer Request>`, which inherits h3's `EventHandlerRequest` constraint, so a slot h3 would refuse reads as `never` for the whole route, body included, with no error anywhere. The body passes through as declared (h3 types it `any`). The query goes through `NativeQuery`: a record is restated key for key, which gives an interface-typed input the implicit index signature h3's `QueryObject` needs, and each value h3's query cannot carry (`unknown` from every `z.coerce.*`, `bigint`, `symbol`) is widened to ufo's `QueryValue | QueryValue[]`, so a coerce query stays typed natively with its keys checked; a query that is no record (an array, a primitive) is `never`, as Nuxt's extractor would answer anyway, so it cannot take the body down with it. Our own slots are untouched by any of this.
- **The two-mechanism agreement** (`test/fixtures/native/checks/agreement.spec-d.ts`, compiled by `test/e2e/native-engine.test.ts` on Nuxt 4.6 and later): the slot through Nuxt's extractor and the map agree on body and query per handler and per route wherever both can be exact. Pinned differences, our map the more accurate side of each: array and primitive bodies and queries (Nuxt reads records only), a body admitting `undefined` (`unknown` included; Nuxt applies `NonNullable`), a body union of records and non-records (Nuxt keeps the records), two handlers on one route and method (Nuxt types neither), and a foreign handler filling the slot itself (no brand for our map to read). A coerce query is typed on both: the same keys, the native side carrying each value no query can carry as any query value.
- **The output delivery** (`src/runtime/server/io/respond.ts`): `responseDelivery(output)` runs at declaration. A Standard Schema (`isStandardSchema`) is the bare form; a plain object without `~standard` (a null prototype passes) is a status map, each slot of which must be a Standard Schema or `null`, else a `declarationFault` naming the status; a map naming no status declares nothing, as an empty `input` or `errors` does; anything else is a `declarationFault` naming what was given. The bare form calls `setResponseStatus(event, 200)` before the check, so a status the Handler or a middleware set cannot carry the `200` body, and passes the Handler's value through. The map form unwraps the Respond helper's envelope, recognised only by the module-private `Symbol('better-handler:responded')` (a plain return or a structural lookalike is a `developerFault` in production too, as no status can be read off it), sets the responded status, and sends the body, or `null` (h3's no-body answer) when the status is declared `null`, whatever a plain-JavaScript caller passed. h3 v1 turns a returned `null` under status `200` into a `204`, so a bodiless `200` (a map's `200: null`, or the bare form's Handler returning a nullable schema's `null`) is sent by `noBody` itself, through h3's `send(event, '')` before the wrapper settles: no `content-type`, `content-length: 0`, and the settled value still `null`. Nitro's `beforeResponse` hooks then run after that reply's headers are out. Every other bodiless status is left to h3. Besides the source readers' helpers, its `setResponseStatus` and `send` are the only h3 runtime imports outside the h3 seam.
- **The response development check** (`src/runtime/server/io/response-check.ts`), behind the shared `devChecks` flag and each refusal a `developerFault`: on the map form an undeclared status is refused before it reaches the response (looked up with `Object.hasOwn`, so a status declared `null` counts as declared), naming the route, the status and the statuses the map names; on both forms the handed-over value is validated against its status's schema, awaited, and refused naming the route, the status and the issues (paths projected with `projectPath`, a root issue named `the response body`); a schema that throws is a fault keeping what it threw as its `cause`; a status declared `null` has nothing to check. The result is discarded, so a development server sends the bytes production sends.
- **The output types** (`src/runtime/types/io/output.ts`): `StatusMap`, `ResponseOutput`, `ResponseOutputs` (status to the schema's output type, the bare form a single `200`, `null` for a bodiless status), `ResponseBodies`, `HandlerReturn` (what the Handler must return: the schema's output, or `Responded<…>` for a map), `SentResponse` (what the returned Handler answers with: the bare schema's output type, the union of the mapped bodies, or the Handler's own settled return without `output`), `Responded` (opaque, keyed by a module-private `unique symbol`) and `Respond`, one signature whose value rides `ArgsFor` as the Fail helper's fields do. `IsStatusMap` answers a schema first, then requires a key, so `{}` declares nothing to `respond`, to the return type and to the guard alike (`HasOutput`).
- **The Response-output slot** (`src/runtime/types/handler.ts`): `BetterEventHandler` carries `ResponseOutputs<Output>` under a third module-private `unique symbol` key, read by `ResponseOutputOfHandler` with the same degradation as the other two; a route declaring no `output` carries `never`.
